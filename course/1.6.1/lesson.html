  • Divide and conquer: split in halves, sort each half, merge the two sorted halves with two pointers.
  • O(n log n) always: log₂ n levels of splitting, n work to merge each level. It is stable (equal elements keep their order) but needs O(n) extra memory.
  • The merge alone is precious: it sorts data bigger than memory (sort chunks, then merge them) and merges sorted streams.

The problem

Sorting by comparing neighbours and swapping (bubble sort, insertion sort) is O(n²): a million values means about 10¹² steps. And the earliest computers had tiny memories but tapes: data that did not fit had to be sorted in pieces, then combined.

Where it comes from

Merge sort is credited to John von Neumann, who wrote it by hand in 1945 as one of the first programs for the EDVAC, a stored-program computer then being designed; Knuth's The Art of Computer Programming attributes it to him. Merging sorted tapes was how big files were sorted for decades, and it is still how data that does not fit in memory is sorted (project 1.6.3).

The idea

A slice of one element is sorted. Two sorted slices merge into one in a single pass (1.5.2). So: split until the pieces are single elements, then merge back up. Every level of merging touches all n elements once, and there are log₂ n levels: n log n comparisons, whatever the input.

Why stability matters

Sort the chemical elements by atomic number, then sort them by period with a stable sort: within each period, they are still in order of atomic number. With an unstable sort, that second order is lost. Go has both: sort.Stable / slices.SortStableFunc (a merge-based algorithm) and the faster, unstable sort.Sort / slices.Sort (1.6.2).
