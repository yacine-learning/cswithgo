  • Pick a pivot, partition the slice into smaller | pivot | larger, then sort both sides the same way. It works in place: no extra array.
  • O(n log n) on average, O(n²) when the pivots are bad (already-sorted input with the last element as pivot). A random or median-of-three pivot makes the bad case very unlikely.
  • Go's sort.Sort and slices.Sort use pdqsort (since Go 1.19): quicksort that detects patterns and falls back to heapsort, so it is never O(n²). Partition alone gives quickselect: the k-th smallest (a percentile) in O(n) on average.

The problem

Merge sort is always O(n log n), but it needs a second array as big as the input. Memory was precious in 1960, and it still matters for big in-memory sorts. Can you sort as fast, moving elements around inside the one array?

Where it comes from

In 1959 Tony Hoare, a 25-year-old British student at Moscow State University, was working on machine translation from Russian to English. To look words up in a dictionary stored in order on magnetic tape, he first had to sort the words of each sentence, and invented quicksort to do it. Back in England, at Elliott Brothers, he was asked to implement a slower sort (Shellsort) and bet his boss sixpence that he knew a faster one; he won the bet. He published Quicksort, Partition and Find (quickselect) in 1961, and received the Turing Award in 1980. He died in March 2026.

The idea

After one partition, the pivot is exactly where it will be in the sorted result, and no element ever crosses it again. A good pivot splits the range in two halves: log₂ n levels of n work. A bad pivot (the smallest or largest value) peels off one element per level: n levels, n²/2 comparisons.
