Keep this
  • An array is one block of memory: element i sits at start + i × size, so reading any index is O(1), and walking it in order is the fastest thing a CPU does.
  • A Go slice is a small header (pointer, length, capacity) over an array. append writes in place while there is room; when full, it allocates a bigger array and copies. Because it grows by a factor, appending is O(1) on average (amortized).
  • Two slices can share one array: writing through one changes the other. When you know the size, make([]T, 0, n); when you need independence, copy.

The problem

You need to keep a sequence: the digits of a number, the moves of a game, the samples of a measurement. Two wishes conflict: reach any element instantly, and add elements without knowing in advance how many there will be. A fixed block of memory gives the first; growing it means finding a bigger block and moving everything.

Where it comes from

Memory has been a row of numbered cells since the first stored-program computers of the late 1940s; an array is simply a run of consecutive cells, and the index is arithmetic on the address. The growing array came later with dynamic languages and libraries. Why "grow by doubling" is cheap was put on firm ground by Robert Tarjan in 1985, who named and formalised amortized analysis: the rare expensive copy is paid for by the many cheap appends around it.

The idea

Doubling from 1 to 1 024 copies 1 + 2 + 4 + … + 512 = 1 023 elements: fewer than one copy per element pushed. Growing by one instead copies 1 + 2 + … + 1 023 ≈ 520 000. The first is O(n) for n pushes, the second O(n²).

The slice header is what you pass around. s[2:5] makes a new header on the same array; append on a slice with spare capacity writes into that shared array. That is fast, and the source of a classic bug (exercise e3).

What Go's append really does

Go's runtime doubles small slices and grows large ones by a smaller factor (about 1.25×) to waste less memory; the exact rule is in growslice in the runtime and has changed between versions. Run e1 to see it on this Go version. A factor, any factor above 1, keeps append amortized O(1).

A small slice that points into a huge array keeps the whole array alive for the garbage collector. When you keep a few bytes from a big buffer, copy them out.
