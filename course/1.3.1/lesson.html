  • A recursive function solves a problem by calling itself on a smaller piece, and needs a base case that stops.
  • Each call gets its own frame on the call stack. A call pauses while the call inside it runs, then resumes at the next line, like a bookmark. The stack is how the program knows where to come back to (1.2.3).
  • Recursion fits trees and divide-and-conquer. For one straight path, a loop is simpler and uses no stack. Two traps: too deep (stack overflow) and the same work done many times (memoize it).

The problem

Some problems are made of smaller copies of themselves. A directory contains directories. A JSON object contains objects. An expression contains expressions. Writing a loop for "go down as deep as it goes, then come back up" means keeping track by hand of where you were at each level.

Where it comes from

Early languages such as FORTRAN gave each subroutine one fixed area for its variables, so a subroutine could not call itself: the second call would overwrite the first one's variables. In 1960, John McCarthy's paper on Lisp defined functions recursively, and Edsger Dijkstra published "Recursive Programming", showing how a stack of frames (borrowed from Bauer and Samelson, 1.2.3) lets every call have its own variables. Dijkstra and Van Wijngaarden had argued for recursive procedures in ALGOL 60, and Dijkstra and Zonneveld's ALGOL 60 compiler, working in June 1960, proved it could be done on a small machine. Every language you use today works this way.

The idea

Trust the recursive call to do its part on the smaller piece; write only how to combine the results and when to stop. When a call returns, Go pops its frame and the caller continues exactly where it paused, with its own variables untouched.

Recursion or a loop?

Any recursion can be written as a loop with an explicit stack, and any loop as recursion. Choose by shape: branching (a tree, two halves) reads better recursive; a single path (follow .Left to the minimum, walk a list) reads better as a loop and costs no stack. Go's goroutine stacks grow as needed, so deep recursion is less fatal than in C, but a million frames still cost memory.

Naive Fibonacci calls Fib(n-1) and Fib(n-2), and each of those calls the same smaller values again: the calls grow like 1.6ⁿ. Remembering each result once (memoization) makes it O(n). That idea, solving overlapping subproblems once, is the start of dynamic programming.
