What this project practises
  • Divide and conquer where the division is forced by memory, not chosen.
  • The merge (1.5.2, 1.6.1) as the tool that combines sorted pieces of any size, reading each one in order.
  • Counting passes over the data: with runs of size m, n lines take ⌈log₂(n/m)⌉ merge rounds, each reading and writing everything once.

The situation

You need to sort a 50 GB access log on a machine with 8 GB of RAM: sort does it, and so do databases building an index, and MapReduce between its map and reduce steps. They all use the method of the tape era: sort pieces that fit in memory, write them out as runs, then merge runs. Merging needs only the head of each run in memory, so the runs can be of any size.

memory: 3 lines        input: g c a h e b f d

runs (sorted pieces):  [a c g] [b e h] [d f]
round 1:               [a b c e g h] [d f]
round 2:               [a b c d e f g h]       3 runs, 2 rounds

Real implementations merge many runs at once rather than two (a k-way merge with a heap: project 1.7.2), which cuts the number of rounds.
